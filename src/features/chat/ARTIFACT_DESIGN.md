# Design Note: Binary Artifacts — The Path to PDF, ZIP and XLSX Tools

Status: **design, not yet implemented.** This note records the decisions so the
implementation is a resume, not a re-derivation. Written as part of the
self-directed-tool-use plan (Phase 6); everything else in that plan has shipped.

## The problem

Every tool the agent has today returns **text**. That is why `generate_csv`
took an afternoon and `generate_pdf` never shipped: a CSV is a string the
result transport already carries; a PDF is bytes with a MIME type and no
protocol for reaching the user's hands.

## The contract

A tool that produces a file returns a `FileArtifact` alongside its text
result, instead of inlining the bytes:

```ts
// features/chat/types.ts
export interface FileArtifact {
  name: string;            // "report.pdf" — model-proposed, sanitized
  mime: string;            // "application/pdf"
  bytes: Uint8Array;       // never base64-in-the-transcript
  size: number;
  summary: string;         // the activity-row line
}
```

`ToolCallResult` gains one optional field: `artifact?: FileArtifact`. The
`data` payload stays text — the *description* of what was produced ("2 pages,
3 sections") — so every existing consumer (turn log, compaction, delegation)
keeps working unchanged.

## The plumbing (three seams)

1. **Executor → engine.** Executors in `lib/app-tools.ts` / a new
   `lib/artifact-tools.ts` build the artifact and return it in the result.
   No transport changes: `ToolCallResult` already flows to the engine as an
   object; only `serializeToolResult` must strip the bytes before the payload
   reaches the wire (the transcript carries `artifactId`, name, mime, size —
   never the bytes).

2. **Engine → storage.** The tool phase, after `record`, hands any artifact to
   a new `services/artifact-store.ts`: writes bytes under IDB keyed
   `conversationId/artifactId`, records `{ artifactId, name, mime, size,
   createdAt }` on the message. One capability: artifacts die with their
   conversation (register a thread-scoped resource, like every other cache).

3. **Storage → user.** The transcript activity row for a tool with an
   artifact renders a **Save / Open** pair. Save uses the existing
   download path; Open is PDF-preview only at first. No agent autonomy here:
   the agent *produced* a file; the user decides what leaves the app. This is
   the `http_write` lesson — capability without a human decision at the exit
   point is a vulnerability someone has to remember to close.

## The gate integration

`secrets_scan` and `assessPushPolicy` gain one rule: an artifact whose
`mime` is `application/zip` (or whose name matches an archive pattern) is a
**warn** on the change set it was attached to, because a zip is the classic
exfiltration/attachment shape. Artifacts are NOT pushable — they never enter
the workspace tree — so the gate only ever sees them as warnings, never as
content to commit.

## The first three tools it unlocks

| Tool | Library | Notes |
|---|---|---|
| `generate_pdf` | `pdf-lib` | text/HTML-lite → PDF; check bundle impact; lazy `import()` inside the executor so chat-only users never pay |
| `generate_zip` | `fflate` | workspace paths → archive; pair with push gate warnings |
| `generate_xlsx` | SheetJS CE | rows → workbook; `generate_csv` remains the zero-dep path for simple exports |

Each follows the standard recipe: registry entry (`planSafe: true`,
`repoFree: true`, `cacheable: false`), contract in `tool-contracts.ts`
(`effects: "none"` — the artifact leaves nothing in the workspace until the
user saves it; `autonomy: "act"`), a `REPO_UTILITY_GROUP`-adjacent prompt
bullet, and the lean-surface decision recorded in `LEAN_SURFACE_TODAY` only
after the artifact path is proven with tests.

## What is deliberately out of scope

- Byte-range streaming of huge files: IDB handles tens of MB fine; anything
  bigger should be generated by a command (`run_command`) in the workspace.
- Serving artifacts to `open_in_tool` targets (charts in DrawFlows): a
  follow-up that reuses the same store.
- Agent-initiated saves to disk: native save dialogs are a desktop-shell
  capability and need their own consent model.
